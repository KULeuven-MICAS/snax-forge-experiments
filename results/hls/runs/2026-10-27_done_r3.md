## Pins (step 4)

In each top, every pin has `<pin>_ap_vld`. Every `<pin>_preg <= <pin>;` sits under one of two enables, which differ only in operand order:

```
E1: if ((~((1'b1 == ap_CS_fsm_state1) & (ap_start == 1'b0)) & (loop_count_ap_vld == 1'b1))) begin
E2: if ((~((ap_start == 1'b0) & (1'b1 == ap_CS_fsm_state1)) & (loop_count_ap_vld == 1'b1))) begin
```

`len_preg` uses the same enable with `len_ap_vld`. The unopt/opt compares read the ap_vld mux, for example `vsum/opt_w4/vsum.v:344-347`: `if ((loop_count_ap_vld == 1'b1)) loop_count_in_sig = loop_count; else loop_count_in_sig = loop_count_preg;`.

**No top reads a pin's port without an ap_vld condition.** Outside its declaration, the port list, the `_preg` load and the `_in_sig` mux, a pin port appears nowhere. In the DaCe tops, `loop_count_in_sig` is truncated into a register written only in the start state, and the loop (in a sub-module for dot, vsum and DaCe W4/W8) uses that register. ## Odd things

- **The 2 cycles opt lost against f6426a6 are a change in loop structure.** In f6426a6, the 12 opt tops and vecadd/vecmul dace_w1 were a single FSM state with `*_flow_control_loop_pipe`, and cosim ran 2 below csynth. Now they have 3 states (state1, pp0, state4) and no flow-control module, and cosim equals csynth. These 14 points are exactly the ones still 2 above f6426a6; no other point changed its state count. Any pin interface whose read Vitis must schedule (`-register`, `ap_vld`) seems to cost the free-running loop form.
- In the unopt/opt tops, the compares read `*_in_sig`, which is the port itself in the cycle `ap_vld` is high. With the one-cycle pulse that is the start cycle only. A driver that holds `ap_vld` high would move the bound mid-run, as before.
- csynth clock estimates match 0b3c268's: vecadd opt and vecadd dace_w1 meet 3.33 ns (2.101 and 2.091 ns), and vsum opt is at 3.023 ns, still `missed` with an uncertainty of 0.90.
- dot dace and vsum dace have a `len`/`len_ap_vld` port pair that nothing reads.
