# Run note: HCMP1 R7c, matvec_col and tier A rebuilt in Vitis and Bambu, 28 Nov 2026

R7b's five kernels (matvec_col; tier A's mvt, bicg, atax, gesummv) from the sources the chat rewrote so Bambu could pipeline them (hls-exercises `6c7572b`): every top computes everything every beat and branches only around the per-row reads and writes; matvec_col keeps its sums in one beat-wide register; gesummv forms alpha (A x) + beta (B x) every beat; mvt reads x2's start value and the bank, then selects; atax is two loops, BEAT and DRAIN; `bench/bambu.py` unrolls every `<NAME>LANE:` loop. Algorithm, stream order and storage are R7b's.

**Result:** Vitis: 5 of 5 pass at II = 1 (atax's BEAT and DRAIN both), cycles as R7b (atax 526 against 523). Bambu: 5 of 5 now build (mvt's front-end crash is gone) and pass every output and the stall run, but Bambu still pipelines none of them: matvec_col is refused at II 1 and 2 as in R7b, the other four have no loop-pipelining line. Bambu's own CFG shows why: in mvt, bicg and atax each loop is still several basic blocks, split by the variable index into the completely partitioned bank (and atax's buffer), not by the per-row reads (those are predicated); in gesummv the compiler sank beta's product into the branch of the row's last beat. The rows stay as built.

**Why no pipelining line.** Bambu's default log says only `loop pipelining: none`, so each of the five was built once more in `build/diag_r7c/<kernel>/` (not kept in git) with the same command plus `--print-dot`, and its CFG (`BB_CFG.dot`) and loop forest (`LF.dot`) read:

- **bicg:** `BEAT` is BB2, BB13 and BB6. Every stream read is if-converted to a predicated read in BB2 (A, p, and r under the row's first beat); the writes are predicated too (s in BB13, q in BB6). BB2 and BB13 each end in a branch whose condition is `k == 0 | k == 1 | ... | k == 7` (k the beat-in-row counter, `_10565`), the false edge leaving the loop to the function's `return`: the read `cur = bank[k]` and the write `bank[k] = nv` of the completely partitioned bank, lowered to a switch over k whose default (k ≥ 8, never taken) is an exit. BB6 ends with the loop's own test.
- **mvt:** `BEAT` is BB2, BB12 and BB20, split the same way: BB2 and BB12 end in k-in-0..7 range checks (`_10459`) with exits to `return`; BB12 also loads a 16-byte vector through a pointer to an internal array; BB20 has the loop test. y2's and x1_in's reads are predicated in BB2.
- **atax:** `BEAT` (BB6, BB7, BB11) and `DRAIN` (BB2, BB4) the same: BB6, BB11 and BB2 end in k-in-0..7 checks on the buffer and the bank, exits to `return`; BB7 and BB4 hold the loops' tests.
- **gesummv:** `BEAT` is BB2, BB4 and BB5 with no exit to `return`: BB2 ends in `cnt == len` (the row's last beat), whose block BB5 holds `_10604 * beta`, the add and the `out` write; the compiler sank beta's product into the write's branch, so the branch holds a multiply and an add besides the write.
- **matvec_col:** `BEAT` is one block (BB2) with every read and the q write predicated; Bambu tries II 1 and 2 and logs only `Loop pipelining not possible for loop (BB2)`, no reason.

So the per-row scalar reads (mvt's y2 and x1_in, bicg's r) are not what blocks Bambu: they are predicated. What splits the loops is the bank's (and atax's buffer's) variable index, and in gesummv the sunk product. No source was changed for Bambu (the prompt's rule).
