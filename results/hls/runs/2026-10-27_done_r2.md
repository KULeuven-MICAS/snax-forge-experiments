## Pin registers

In `rtl/done/vsum/opt_w4/vsum.v`:

```
179:         len_0_data_reg <= len;
185:         loop_count_0_data_reg <= loop_count;
379: assign icmp_ln14_fu_115_p2 = ((b_fu_68 == loop_count_0_data_reg) ? 1'b1 : 1'b0);
383: assign icmp_ln22_fu_169_p2 = ((add_ln22_fu_163_p2 == len_0_data_reg) ? 1'b1 : 1'b0);
```

The method was to scan every top for `<pin>_0_data_reg <= <pin>;` and for any read of the raw port. The table shows whether each pin is registered. No top reads a pin's port directly anywhere.

| kernel/case | W1 | W4 | W8 |
|---|---|---|---|
| dot unopt, dot opt, vsum unopt, vsum opt | loop_count yes, len yes | same | same |
| vecadd and vecmul, unopt / opt / dace | loop_count yes (no `len` pin) | same | same |
| dot dace, vsum dace | loop_count yes; len no: unused port | - | - |

**The register is not a one-shot sample at ap_start.** `loop_count_0_vld_reg` and `len_0_vld_reg` are set by `#0 ... = 1'b0` and never written, and this holds in all 32 tops. The load enable (line 184) therefore reduces to `~(ap_CS_fsm_state1 & ~ap_start)`:

```
184: if (((~((1'b1 == ap_CS_fsm_state1) & (ap_start == 1'b0)) & (loop_count_0_ack_out == 1'b1) & (1'b1 == 1'b1) & (loop_count_0_vld_reg == 1'b1)) | (~((1'b1 == ap_CS_fsm_state1) & (ap_start == 1'b0)) & (1'b1 == 1'b1) & (loop_count_0_vld_reg == 1'b0)))) begin
185:     loop_count_0_data_reg <= loop_count;
```

The register reloads on every cycle from the ap_start cycle until the FSM returns to idle (state1 → state2 → pipeline → state5). It follows the port one cycle late for the whole run. The pin is now off the port-to-compare path, but a pin changed mid-run still changes the loop bound. The comments in `run_bench.tcl` and `lanes.h` ("the driver may change them during the run") do not hold, so forge's sample-at-start is still not matched.

## Odd things

- **The pin registers reload every cycle while the block runs.** See "Pin registers" above. Sampling once at ap_start likely needs either a capture the code controls (for example, register the value in the C++ under a start-only condition) or the `s_axilite`/`ap_vld` handshake on the pins. Not tried.
- **The opt tops (every kernel, every W) and vecadd/vecmul dace_w1 changed shape, not only gained a register.** `*_flow_control_loop_pipe.v` is gone from all 14 folders. In f6426a6, `vsum/opt_w4/vsum.v` had a single FSM state (`ap_ST_fsm_pp0_stage0`). Now it has state1 → state2 → pp0 → state5, so the pipeline has an entry state and an exit state. That likely explains opt cosim +3 against unopt +1. vecadd/vecmul dace_w1 also gain a 31-bit `trunc_ln19_reg_122` and +725 µm², against about +380 for W4/W8. The csynth clock estimate for vecadd dace_w1 drops from 2.518 to 2.091 ns (missed → met).
- csynth timing at 3.33 ns improves where the pin sat on the compare path. vecadd opt (all W) goes from 2.528 to 2.101 ns, missed → met. vsum opt goes from 3.450 to 3.023 ns and is still `missed`, with an uncertainty of 0.90. DC's 10 ns critical paths barely move (±0.15 ns).
- dot dace and vsum dace keep a `len` input port that nothing reads, so it gets no register. The tops ignore `len`, as they did in f6426a6.
