# Run note: SYN1 R2, the power flow for snax-forge's netlists, probed on two points, 31 Oct 2026

The HLS power flow (`docs/power.md`, X7 to X20: zero-delay Questa on the mapped netlist, VCD, vcd2saif, PrimePower) with a forge adapter in place of the HLS one: `pwr ... --source forge`. The DUT is the whole wrapper `snax_forge_shell_wrapper` as DC wrote it in R1 and R1b (X6), driven through its CSRs; the TB plays the streamers, always valid and always ready. One size, `n2048`. R3 runs every point.

**Both probes pass on both technologies.** `done/vecadd/forge_w4` and `done/dot/forge5_w4`: every output matched, the window's cycles equal the COUNTER read back and snax-forge's own model (512 and 517), the SAIF and annotation checks pass, and the modules add up to the top.

## Step 1: `sim/sources/forge.py`

- `tb.json` from the bundle (`point.json`, `bundle.json`, `accelerator.json`, the streamer hjson's `num_channel`) and the netlist's port list. Every port of the netlist is covered, as C§17's wrapper names them; a point with more than one group, a second JOB_BEATS or another read-write CSR is refused.
- What only snax-forge knows comes from snax-forge's own code, through `forge/query.py`, run in snax-forge's pixi environment with `forge/bundles.py`'s cleaned environment (`PIXI_*`, `CONDA_*` and this repo's `.pixi` off PATH): each outer port's container (the design point's graph, as snax-forge's `gen/rtl.py` `vectors` finds it: A, B, C for vecadd and vecmul, A, B, out for dot, A, out for vsum), the recipe's kernel, and the group's cycles from `gen/rtl.py`'s `group_counter` with JOBS and the units' T as the program writes them.
- Control `forge_csr` (the kind `sources/hls.py` had reserved): the CSR port, `<group>_busy_o`, `<group>_done_o` and the CSR offsets from `accelerator.json`. The writes for `n2048`: vecadd and vecmul JOBS = 2048 / W; vsum_tree and dot 2 to 6 JOBS = 1 and the fold's JOB_BEATS = 2048 / W (on `sum` for dot 2 and 3, `mac` for dot 4 to 6, `acc` for vsum); then START.
- All 48 forge points build a `tb.json` (0 refused). Their expected cycles are C§17's: vecadd and vecmul 2048 / W; vsum T + 1; dot 2 T + 2, dot 3 T + 1, dot 4 T + 2, dot 5 T + W + 1, dot 6 T + W + 2 (T = 2048 / W, J = 1), from 2051 (dot_6 W = 1) down to 64 (vecadd W = 32).
- `pwr tbjson`, `run`, `summary` and `setup-check` take `--source hls|forge`, default `hls`. **The HLS dry path is unchanged:** `pwr tbjson` of `done/vecadd/opt_w8`, `done/dot/opt_w4`, `done/vsum/unopt_w2` and `untiered/rowsum/opt_w4` is byte-identical to before the change. No HLS point was rerun and `results/hls/` did not change.

**A fix found on the way.** Since SYN1 R0, `syn/scripts/constraints.sdc` names the clock and reset as `$clk_port` and `$rst_port`, which `dc_syn.tcl` sets; `sim/scripts/pt_power.tcl` and `sim/probe/dc_readback.tcl` source the same file and did not set them, so PT and the setup check would have stopped at `create_clock` for HLS too (no HLS power run has happened since R0). Both now read them from the run's `tech.json` (`dc_env`'s `SYN_CLK_PORT`, `SYN_RST_PORT`), else `ap_clk` and `ap_rst_n`; the uniform mode's clock exclusion uses `$clk_port`. Checked on HLS without touching `sim/runs/` or `results/hls/`: PT on `done/vecadd/opt_w8`'s existing nangate45 SAIF, in a scratch folder, gives the same `power.rpt` groups and a `power_hierarchy.rpt` identical to the committed run's.

## Step 2: the testbench

- `sim/tb/csr_seq.sv`: `rst_ni` low for 5 cycles, released at a falling edge, 2 idle cycles; each CSR write offered from a rising edge until a falling edge samples `csr_req_ready_o` (the task samples the DUT itself at that edge; a copy taken by another block at the same edge would race), `csr_rsp_ready_i` always 1. snax-forge's CSR block answers a read in the cycle it is taken and a write not at all, as its `ShellDriver` assumes.
- `go` rises with the START write, so the sources are valid from the first busy cycle, as `group_counter` assumes (every input valid).
- The window opens at the falling edge before the edge that accepts START and closes at the falling edge before e_E, one cycle before the first falling edge that sees `<group>_done_o` = 1 (high in E + 1, C§17): E - a rising edges, which is COUNTER. Dumping runs from the edge offering START to the edge after done is seen, around the window (PITFALLS Q6); the SAIF's `clk_i` TC = 2 x cycles confirms no boundary edge was lost. COUNTER is then read over the CSR port.
- `tb_top` builds the forge top from `tb.json` as it builds the HLS one (`axis_src`, `axis_sink`, the dump scopes); every module of the netlist got a dump scope (PITFALLS DC6), checked at compile.

## Step 3: stimulus, reference and checks

- rand64 (X19): 2048 full-range int64 per input stream, seed 0, stream by stream in `tb.json` order; 512 beats at W = 4; every input bit toggles.
- **Reference cross-check, and how.** `sim/ref.py` is compared once per kernel, size and seed in each batch with snax-forge's kernel body: `forge/query.py ref` loads `kernels/polybench/<kernel>.py` through snax-forge's `sdfg/loader.py` and calls its `SPEC.func` (`vecadd(A, B, C)`: `C[:] = A + B`; `dot(A, B, out)`: `out[0] = np.sum(A * B)`) on the same inputs, its outputs zero-filled at the SPEC's shapes. Equal for vecadd and dot in all four runs (`ref_check` in `result.json`); also checked by hand on the same rand64 inputs for vecmul and vsum, equal.
- Cycles: window = COUNTER = expected in all four runs. SAIF: DURATION = cycles x 10 ns, `clk_i` TC = 2 x cycles, T0 + T1 + TX = DURATION on every driven net.
- **Annotation: 60 floating nets** (PITFALLS PT6). On vecadd (both technologies) and dot_5 on nangate15, PT left 60 nets at default: `ctrl/io_groups_0_status[2..31]` and `csr/io_status_0[2..31]`, STATUS's constant bits, which DC left as bit-blasted ports with no driver and no cell pin; vcd2saif has them at Z for the whole window. Forced to toggle rate 0 they change nothing (vecadd nangate45: every group the same to seven digits). The forge check takes such nets out of the denominator and records them; every other net was annotated (2130 of 2130, 23550 of 23550, 2181 of 2181, 28082 of 28082). dot_5 on nangate45 had no floating net.

## Odd or open

- **The setup check on nangate15 fails on the forge point** (PITFALLS PT5): `pwr setup-check --source forge` on `done/vecadd/forge_w4` passes on nangate45 (every group within 0.02 %), but nangate15's register group is -0.55 % (switching -1.49 %), over its 0.1 %; combinational +1.17 % is within its 2.5 %. The activity is the same in both tools; holding `rst_ni` static changes nothing; a few register-driven nets have up to 1.5 % less load in PT; only nangate15 has `rise/fall_capacitance_range`, the switching difference PT5 already found on NAND2/NOR2. PT stays the reference (X10); whether forge's nangate15 register group gets its own tolerance is for R4's X-numbers.
- The HLS flow's PT and setup-check scripts were broken by R0's `constraints.sdc` change until this round (fixed above); an HLS power rerun after this round would be the first since R0.
- PT threads: with J = 20 from the licences, each PT run had 1 thread even for a batch of two points (as for HLS, X16); R3's 48 points use the workers.
