# HSYN1 R8: the tier comparison CSVs (2026-11-05)

Written by Claude in its own sandbox, not on the server: `report/compare.py` reads only CSVs committed on `ry/hsyn1` (after `hsyn1-r7`, 77a480c), so it needs no tool, licence or checkout next to the repo. Nothing in snax-forge was read or run.

## What

`report/compare.py` (`pixi run compare`, X45) writes `results/compare_done.csv` and `results/compare_untiered.csv`: one row per tech, tier, kernel, W, tool, case and size, for forge and the four HLS cases (Vitis opt and dace, Bambu, XLS) with W <= 16 (X38), on nangate45 and nangate15. The columns are listed in X45 and in the script's docstring. The data is laid out only: no ratios, no rankings.

## Checks (all pass)

- Every listed point has a row on both technologies.
- Every ok point has the same sizes as the other points of its kernel; every tier-done HLS point has n2048; every forge point has n2048.
- Every power run is ok; the only rows that are not ok are the three parked RAM points per technology (status `syn: skipped: needs a RAM macro`).
- No key repeats.
- Where a split exists (forge: csr, ctrl, datapath, glue; Bambu: ctrl, datapath, glue), it sums to `area_um2` within 0.01 um2.
- The per-part energies (`e_dyn_<part>_pj`, from `power_pt_modules.csv`) come from each point's default run (`parts_size`): forge n2048, Bambu b64, and Bambu rowsum m8_n64 (rowsum's default, X19). Forge's wrapper holds nothing but csr, ctrl and dp, so its glue energy is PT's rounding (at most 6e-7 of the total, sometimes negative); `compare.py` writes a glue within 1e-5 of the total as 0. Bambu's glue (done_delayed_REG) stays as measured.
- Every ok row has `rtl_commit`: forge `snax_forge_commit` (f9764d5); Vitis 4ef8bc8 (R2's bench run); Bambu and XLS the `git` column of their cycle CSVs, the commit each point was measured at (Bambu 542fa32; XLS faf5a3d and 46fa843 for tier done, 9ae29ea for untiered, by XLS1 round).

## Notes on the columns

- `cycles` is each tool's own window (`window` names it): Vitis `ap_start` to `ap_done` (X12), forge START to done (X13), Bambu `start_port` to `done_port`, and XLS the cfg transfer to the last output with the last edge included (X44). The windows differ by a cycle or two by definition, which matters only at the smallest sizes.
- `elements` is beats x W, the elements of one input stream; `pj_per_elem` is `e_run_pj` over it.
- `leak_dc_uw` is DC's leakage estimate; power is dynamic only (X7).
- The path-class slacks are empty on forge's rows, which were synthesized in SYN2, before X40.

## R9: results/compare_hls.md (step 1, generated parts)

`report/compare_hls.py` (`pixi run compare-hls`, X46) writes `results/compare_hls.md` and 8 figures in `results/compare_hls/`, from the two tier CSVs only: the four HLS cases per kernel, area, energy per task, latency per task and power against W, on nangate45 (tier done at n2048, untiered at each kernel's larger task size), with a setup table and a nangate15 check. Power computed as E_run / (cycles x 10 ns) agrees with PrimePower's `p_dyn_uw` within 7e-7 on every row. The order of the cases is the same on both technologies in 109 of 120 comparisons.
