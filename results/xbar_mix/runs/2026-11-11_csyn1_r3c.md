# Run note: CSYN1 Part B R3c, the interconnect with read-only and write-only inputs (xbar_mix), 11 Nov 2026

R3 synthesized the whole cluster (`dot3_w16`, `results/cluster/runs/2026-11-11_csyn1_r3.md`). Against HWCOST, snax-forge's first-order cost model, the TCDM interconnect was the one part far off: HWCOST took 187,547 um2 from STRM1's `results/xbar/nangate45/synth_dc.csv` (between `i32_b32` and `i40_b32`), the cluster's is 107,878 um2. Same RTL (SparseInterconnect, 36 inputs, 32 banks, fully connected); the likely cause is the constants the cluster puts on it, which STRM1's lone points did not have. This round measures them (X70) so R3d can fix HWCOST; nothing is fitted here.

**Result:** 29 points, all ok, 0 errors, 0 licence retries. The template's ties alone take 1.8 to 2.6 % off STRM1's points. All inputs read-only take 38.9 to 40.6 % off the all read-write point, all write-only 40.7 to 41.4 %. The cluster's mix `i36_b32_r32_w1` is 118,952 um2: 35.9 % under `i36_b32_r0_w0` (185,460 um2), and 10.5 % over the cluster's `sparse_interconnect_i` (107,685 um2), the gap all combinational.

## Step 1: the code

- `strm/gen.py`: set `xbar_mix`, point `i{inputs}_b{banks}_r{ro}_w{wo}`; `grid.json`'s `xbar_mix` (axes inputs {16, 32, 64} x banks {16, 32, 64}, mixes `rw`, `ro`, `wo`, two extra points, a `_doc`). A set's points are the axes' product, then its `extra` list; xbar's `extra` is `i36_b32` (its axes unchanged). An xbar_mix point runs no sbt: `make_mix` reads the base zip's `SparseInterconnect.sv`, writes `xbar_mix.wrapper(...)` and zips `SparseInterconnect.sv` (the same bytes), `xbar_mix.sv`, `filelist.f` (`# top: xbar_mix`, both files), `config.json` (the base's config with set, point, params and top its own, plus `base`, `ro`, `wo`, `xbar_mix_md5`) and `point.json` (the base's versions and commits, the SV's md5, both port counts). A missing or stale base is added to the same call's sbt batch. The sbt part moved into `run_sbt`, unchanged.
- `strm/xbar_mix.py`: the wrapper's header comment named empty ranges (`16..15 read-write` for an all read-only point); it now says `no read-write input`. Three header asserts added to `strm/test_xbar_mix.py`. Fixed before any bundle was made, so every `xbar_mix_md5` is the fixed file's (`4af3d0ee...`).
- `syn/syn.py`: source `xbar_mix` (`SYN_RTL_XBAR_MIX`, default `rtl/xbar_mix`; clock `clock`, reset `reset`; in `BUNDLED` and `STRM`), columns `inputs`, `banks`, `ro`, `wo`, `rtl_flop_bits` (`flop_bits` over both files under `xbar_mix`, so the SparseInterconnect's), `flops_removed` (rtl_flop_bits minus DC's flops), `opt1207`, `snax_cluster_commit`. A removed flop is printed per point and does not fail the row; more flops than the RTL, or no count, fails it.
- Checks: `syn.py run '*' --dry-run` at `-j 1` prints byte for byte what it printed before for `xbar` (594 lines) and `streamer` (3,696 lines); at `-j 4` the lines interleave (PITFALLS DC17). `strm-rtl --list` keeps STRM1's 196 lines unchanged and adds `xbar/i36_b32` and the 29 points; `strm-rtl --dry-run` of one xbar and one streamer point is unchanged. Dry runs of one point of each strm source (`streamer d2_l1_c1`, `xbar i36_b32`, `xbar_mix i36_b32_r32_w1`) print the expected file lists and tops; `syn check-ports --source xbar_mix`: 29 of 29 pass. `strm/test_xbar_mix.py`: 4 tests ok, the lint part skipped on the host (no Verilator).

**Ports.** `i36_b32_r32_w1`'s wrapper has 587 ports against SparseInterconnect's 818: 2 + 36 x 12 + 32 x 12 = 818; the template's ties remove 36 + 3 x 32 = 132 (686, `i36_b32_r0_w0`'s count); 32 read-only inputs 3 each (96) and the writer 3 (write, amo, response data) leave 587.

**Flops.** Read-only and read-write points keep every flop the RTL declares (`opt1207` 0). Each write-only input loses its `prevBankRequest` register, log2(banks) bits: `flops_removed` is inputs x log2(banks) on every all write-only point (64 to 384) and 5 on `i36_b32_r32_w1` (its one writer at 32 banks), each one an OPT-1207 line.

**Max-capacitance nets (open).** Three read-only 64-bank points report max-cap violations in `qor.rpt`: `i16_b64_r16_w0` 308, `i32_b64_r32_w0` 1,332, `i64_b64_r64_w0` 848; every other point has 0 (STRM1's xbar points had at most 5). In `i32_b64_r32_w0`'s netlist 4,416 outputs are `assign ... = 1'b0` (64 banks x 69 bits: data, amo, write), none in `i32_b64_r0_w0`'s; the read-only 16- and 32-bank points have such outputs too but no violation (`i16_b16_r16_w0` 1,104, `i32_b32_r32_w0` and `i64_b32_r64_w0` 2,208, each 0 max-cap nets; `i64_b64_r64_w0` 4,416 and 848), so it comes with 64 banks' 4,416 constant outputs. Which nets violate is not in the kept reports. DC fixing them would add buffers, so these three areas may read slightly low; their area ratios match the other read-only points (-40.5 %, -40.5 %, -40.6 %).

The cluster's numbers are from `results/cluster/nangate45/reports/dot3_w16.zip` `area_hierarchy.rpt`, comb and seq summed over each subtree's own columns. The 107,877.9 um2 in the round's brief is the wrapper level; `sparse_interconnect_i` is its child, 192.85 um2 less (PITFALLS DC16). `i36_b32_r0_w0` is 1.1 % under HWCOST's interpolated 187,547 um2.

The cluster's mix closes 86 % of the gap between `i36_b32_r0_w0` and the cluster (66,508 of 77,775 um2). The flops agree to one (435 against 434; 1,967.1 against 1,962.5 um2, one DFF), so the remaining 11,267 um2 is combinational logic the cluster makes constant or dead and `xbar_mix` does not. Candidates, not tested: the template passes each port's `q.user` and `q.user.tcdm_priority` through, and `DataRequestor` drives a reader's priority from a static constant (`higherStaticPriority.B`) when dynamic priority is off, so a streamer port's priority, user and perhaps strb bits may be constants in the cluster; and DC sees the whole cluster around it, so bank-side outputs nothing reads (for example `bits_user`) or the cores' and AXI port's constant fields may be dead or constant there.
