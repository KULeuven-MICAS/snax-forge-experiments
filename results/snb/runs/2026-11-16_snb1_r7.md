## What broke and how the driver got round it

Nothing in a tracked flow file was changed. Forge-only pieces the driver worked around:

- `cluster/cluster.py`'s `swap_check` hard-wires `snax_forge_cluster_wrapper`: the driver has a copy with the wrapper as `snax_snitch_cluster_wrapper` (otherwise the same checks).
- `syn/syn.py`'s cluster source has the top `snax_forge_cluster_wrapper` and the folders `syn/runs/cluster/`, `results/cluster/`: the driver sets `SOURCES["cluster"]["top"]`, `RUNS` and `RESULTS` to the snb ones after `use_source("cluster")`, then calls run_dc, finish_run and write_summary as cluster.py's syn() does. `CLUSTER_COLUMNS` (recipe, W, snax_forge_commit) stay empty in the snb rows.
- cluster.py's steps start from a forge bundle (make_bundle, `snax_forge.hjson`, `forge_expected.txt`, snax-forge-sim and -run, `forge cycles`); the driver uses snax_cluster's cluster files, `make sw` and the snitch-forge programs' own report (`snitch-forge cycles run`, `core <c> compute`, `errors`, `workers`) instead, and builds `bin/snitch_cluster.vsim` with `make bin/snitch_cluster.vsim` (what snax-forge-sim calls).
- snax_cluster's `sw/apps/Makefile` builds the snitch-forge programs only when `CFG_OVERRIDE` is literally `cfg/snax_snitch_cluster_<n>.hjson`: every make call passes that relative path (cluster.py passes an absolute bundle path).
- `cluster/power.py` hard-wires the testbench instance `tb_bin/i_dut/i_snax_forge_cluster` and `snax_forge_cluster_wrapper` (not used tonight; only its vsim_command, which is generic).
