### Window against section

The run windows of mvt and matvec are further from the plain run's section than dot's, and not by the same amount on each config:

| Kernel | snitch1_cg | snitch5_cg | snitch9_cg |
|---|---|---|---|
| dot | -3 (R8) | -12 | -16 |
| mvt | -208 (-0.08 %) | -161 (-0.23 %) | -461 (-1.24 %) |
| matvec | -45 (-0.02 %) | -2 814 (-3.99 %) | +437 (+1.07 %) |

The two ELFs run the same kernel code: the quiet build (`-DQUIET`, `snitch_forge.h`) only writes the marks to CSR 0x7c5 in place of the `mcycle` reads, drops the per-worker tic/toc and prints nothing. But `main` compiles differently: for mvt, `llvm-objdump` gives 438 lines for the plain ELF's `main` and 382 for the quiet one's, with a different register allocation from the first block on. The same two ELFs run on all three configs, yet the gap changes size and sign from config to config; a difference in instruction count would not do that. A per-config interaction with where the code and data land (I-cache refills shared by the workers, or TCDM bank conflicts) would; not checked further. For `snitch5_cg_matvec_int64` the gap is real execution time, not the window's edges: every worker's compute in the plain run (70 469 to 70 494 cycles) is longer than the quiet window (67 701).

What it means for E11: E_run is PT's energy over the quiet ELF's run window, while C_run, the GLS C_run and η_A are the plain ELF's. η_E (n_op / E_run) is unaffected, as E_run and n_op are the same task; a figure that multiplies a power by C_run or divides E_run by it mixes the two runs, by up to 4 % for `snitch5_cg_matvec_int64`. For review: whether to keep this, or to take C_run from the quiet run (its run window) wherever energy is used.
